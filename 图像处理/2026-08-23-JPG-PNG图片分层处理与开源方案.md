# JPG、PNG 图片分层处理与开源方案

> 调研日期：2026-08-23。本文以 GIMP、Krita、OpenRaster、ImageMagick、Pillow、libvips、IOPaint、LaMa、Segment Anything、rembg、Fabric.js 等官方文档或官方仓库为主要资料。项目版本、模型、许可证和 GitHub 数据会变化，正式上线前应按锁定版本复核。

## 结论

普通 JPG/PNG 只有最终的像素结果，不包含原始设计中的图层、文字对象、蒙版或编辑历史。PNG 虽然支持透明通道，但透明通道不等于多图层；JPG 通常还会经过有损压缩。因而“把一张普通图片分层”不是从文件中恢复原始图层，而是根据视觉内容重新构造一套可编辑的图层和蒙版。

推荐把流程拆为四类能力：

1. **工程文件和图层编辑**：用 GIMP 的 XCF、Krita 的 KRA，或跨软件交换用 OpenRaster（ORA）保存图层、透明度、蒙版和顺序；JPG/PNG 只作为导出交付格式。
2. **标准元素叠加**：文字、Logo、边框、标签、二维码等不需要 AI，用透明 PNG/SVG 加到独立图层，再用 ImageMagick、Pillow、libvips 或浏览器画布合成。
3. **对象拆分和背景移除**：人工选择适合边缘要求高的场景；SAM/SAM 2 生成交互式对象蒙版；rembg 适合常见前景抠图。蒙版经过人工修边后，将对象导出成带 alpha 的独立 PNG。
4. **移除、替换和扩图**：先制作需要修改区域的黑白蒙版，再用 Resynthesizer、LaMa/IOPaint 或 Stable Diffusion Inpainting 修补背景。生成式结果必须保留为新图层，并支持重新生成和人工修正。

如果目标是做一个可落地的图片处理产品，比较稳妥的组合是：**Fabric.js 或类似画布负责交互图层和项目 JSON，Pillow/ImageMagick/libvips 负责常规合成，SAM/rembg 负责蒙版，IOPaint/LaMa 负责删除，Stable Diffusion Inpainting 负责添加或替换**。如果主要是人工创作，直接使用 **Krita 或 GIMP** 更快。

## 一、先厘清“分层”是什么

### 1. JPG/PNG 与图层工程文件的区别

| 格式 | 能否保存多个可编辑图层 | 适合用途 | 关键限制 |
| --- | --- | --- | --- |
| JPG/JPEG | 否 | 照片交付、网页图片、打印成品 | 不支持透明；有损压缩；导出后无法恢复文字、蒙版和图层 |
| PNG | 否 | 无损交付、透明元素、Logo、贴纸 | 支持 alpha，但仍是一张合成图；不保存编辑图层 |
| WebP/AVIF | 否 | 更小的网页图片，可带 alpha | 仍是单张合成图，不是图层工程格式 |
| XCF | 是 | GIMP 原生工程 | 适合 GIMP 工作流，跨软件交换能力不如 ORA/PSD |
| KRA | 是 | Krita 原生工程 | 图层、蒙版和 Krita 特性较完整，其他软件支持有限 |
| ORA | 是 | 开源图层交换 | 以 ZIP/XML 和 PNG/SVG 组织图层，效果和高级特性要看软件支持 |
| PSD | 是 | 与 Photoshop 交换 | 事实标准但含有大量软件专属能力，开源软件之间并非完全兼容 |

OpenRaster 官方规范把 ORA 定义为图层栅格图像交换格式：压缩包内用 XML 描述结构，每个栅格图层通常对应一个 PNG，矢量图层可对应 SVG；官方列出的支持软件包括 Krita、GIMP、MyPaint 和 Scribus。它适合在开源软件之间交换基本图层、透明度和顺序，但不能保证 Photoshop 的调整图层、智能对象、字体和复杂混合模式完整往返。

### 2. 从一张扁平图重建图层

一张照片可以按以下方式重建：

```text
原始图片
  ├─ 背景层：保留未拆出的场景或经过修补的背景
  ├─ 对象层：人物、商品、车辆、Logo 等，带 RGBA alpha
  ├─ 文字/矢量层：重新输入的文字、SVG、二维码或图标
  ├─ 蒙版层：对象选择、擦除区域、渐变过渡
  └─ 效果层：颜色、阴影、模糊、边框、水印和其他叠加效果
```

重要的是把“像素”和“决策”分开保存：对象本身是一张透明 PNG 或 SVG，蒙版是一张灰度图，位置、缩放、旋转、透明度和混合模式放在工程元数据里。这样才能在不破坏原图的情况下重新定位水印、替换对象或关闭某个效果。

对于原图中已经被覆盖的区域，不存在可靠的通用算法可以找回真实背景。AI 修补只能根据周围像素和模型先验生成一个合理猜测，不能当作原始内容恢复。

## 二、开源方案总览

### A. 桌面图层编辑器

| 项目 | 许可证/状态 | 分层与编辑能力 | 适合场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| [GIMP](https://www.gimp.org/) | GPL 系列；成熟 | 图层、图层组、alpha、图层蒙版、混合模式、路径、插件、批处理；原生 XCF | 照片编辑、合成、水印、人工修补、脚本自动化 | XCF 最适合 GIMP 自己保存；复杂 PSD 的调整图层和文本兼容性不能视为 Photoshop 等价 |
| [Krita](https://krita.org/) | GPL-3.0；成熟 | 图层、组、透明/变换/滤镜蒙版、矢量图层、文件图层；原生 KRA；支持 ORA/PSD | 插画、海报、概念图、精细蒙版和人工绘制 | 更偏数字绘画；PSD 的高级效果仍可能需要重建 |
| [Graphite](https://github.com/GraphiteEditor/Graphite) | Apache-2.0；仍在 alpha | 节点式、程序化、矢量和栅格编辑方向 | 需要非破坏节点和程序化图形的探索 | 版本和功能仍在快速变化，不宜直接作为唯一生产工具 |
| [Resynthesizer](https://github.com/bootchk/resynthesizer) | GPL-3.0 | GIMP 插件，基于纹理合成修补和移除对象 | 纹理、地面、墙面等重复背景的对象移除 | 不适合所有几何结构；复杂区域通常需要手工修边或多次处理 |

GIMP 官方开发文档目前把 clone/heal 工具称为现有接近方案，并将更智能的通用 inpainting 作为后续方向；Resynthesizer 是实际可用的 GIMP 插件。因此，想要在桌面端“选中后移除”时，可以使用 GIMP/Krita 负责图层和蒙版，另接 Resynthesizer 或 IOPaint，而不应假设 GIMP 内置了与 Photoshop Content-Aware Fill 完全相同的功能。

### B. 程序化合成和批处理

| 项目 | 许可证/状态 | 主要能力 | 适合场景 | 主要限制 |
| --- | --- | --- | --- | --- |
| [ImageMagick](https://github.com/ImageMagick/ImageMagick) | ImageMagick License；成熟 | 命令行和多语言 API；格式转换、缩放、裁剪、alpha、composite、文字和水印 | 批量加水印、批量导出、缩略图、服务端流水线 | 不是交互式图层编辑器；复杂蒙版和颜色管理需要仔细验证 |
| [Pillow](https://github.com/python-pillow/Pillow) | HPND/PIL 许可；成熟 | Python 像素读写、ImageDraw、alpha 合成、滤镜和基础变换 | Python 服务、定制规则、批量处理、与 AI 推理衔接 | 默认不提供完整图层工程模型；复杂处理需自行设计数据结构 |
| [libvips](https://github.com/libvips/libvips) | LGPL-2.1；成熟 | 低内存、高吞吐图像处理，适合缩放、格式转换和合成 | 大量图片、服务端吞吐、内存受限环境 | API 偏底层；它是图像处理库，不是带图层面板的编辑器 |
| [Fabric.js](https://github.com/fabricjs/fabric.js) | MIT；成熟 | 浏览器 Canvas 对象模型，支持移动、缩放、旋转、滤镜，JSON/SVG 序列化 | Web 图片编辑器、贴纸、文字、Logo、水印和对象图层 | 不是完整的 Photoshop 类栅格编辑器；像素级修补和 AI 需要外接服务或模型 |
| [Konva](https://github.com/konvajs/konva) | 开源项目；以仓库 LICENSE 为准 | 浏览器 Canvas 的舞台、图层、节点和交互 | 定制画布、标注、拖拽式合成 | 需要自行设计项目持久化、导出和复杂图像编辑能力 |

常规水印、Logo 和文字不需要 AI，也不需要先把整张图片“AI 分层”。透明 PNG/SVG 加上位置和透明度即可；批量任务优先 ImageMagick、Pillow 或 libvips，交互式 Web 编辑优先 Fabric.js/Konva 一类对象画布。

### C. 分割、抠图和蒙版

| 项目 | 许可证/状态 | 能做什么 | 适合场景 | 关键边界 |
| --- | --- | --- | --- | --- |
| [Segment Anything](https://github.com/facebookresearch/segment-anything) | Apache-2.0；SAM 原始仓库，SAM 2 另有仓库 | 根据点、框或自动提示生成对象 mask | 用户点击对象后拆成独立图层、交互式抠图 | 输出的是 mask，不是最终透明 PNG，也不负责背景修补 |
| [SAM 2](https://github.com/facebookresearch/sam2) | Apache-2.0 | SAM 的后续模型，支持图像和视频分割 | 需要更强交互分割或未来扩展视频 | 模型尺寸、显存、推理速度和具体 checkpoint 需按目标设备评测 |
| [rembg](https://github.com/danielgatis/rembg) | MIT；工具成熟 | 基于模型去除图片背景，提供 CLI、Python 库和服务方式 | 商品图、人像、常见前景的快速抠图 | 对透明物体、细发丝、反光和复杂遮挡仍需人工修边；模型权重许可要单独核查 |

分层拆分的标准链路是：**原图 -> 分割模型或人工选择 -> 黑白 mask -> mask 修边/羽化 -> 复制对象并应用 alpha -> 导出透明 PNG**。不要直接把模型输出当成终稿；毛发、玻璃、阴影和物体接触边界通常需要额外的 matting、颜色去边和人工处理。

### D. 移除、替换和添加新元素

| 项目 | 许可证/状态 | 主要能力 | 推荐用法 | 注意事项 |
| --- | --- | --- | --- | --- |
| [IOPaint](https://github.com/Sanster/IOPaint) | Apache-2.0；可自托管 | Web UI、CLI/API；LaMa 等擦除模型，Stable Diffusion/PowerPaint 等替换和扩图模型 | 选区域移除人物、物体、瑕疵或水印；按提示词添加/替换内容 | 代码开源不代表所有模型和 checkpoint 同许可证；模型下载、显存和结果稳定性需纳入部署方案 |
| [LaMa](https://github.com/advimman/lama) | Apache-2.0 | 大范围纹理感知图像修补，擅长连续纹理和较大 mask | 去除背景中的物体、文字或瑕疵，作为 IOPaint 的擦除后端 | 更适合“补背景”，不擅长按文字提示创造具有明确语义的新对象 |
| [Diffusers](https://github.com/huggingface/diffusers) | Apache-2.0；模型生态广 | Python 扩散模型库，支持 inpainting/outpainting 等管线 | 需要自行控制模型、遮罩、提示词、批量任务和服务 API | 具体模型、VAE、LoRA 和 checkpoint 有独立许可，不能只看库许可证 |
| [ComfyUI](https://github.com/Comfy-Org/ComfyUI) | GPL-3.0；节点生态广 | 节点式 AI 工作流，适合编排分割、ControlNet、inpaint、放大和导出 | 先验证复杂工作流，再封装为内部服务或批处理 | 自定义节点和模型许可证不统一；工作流可复现性需要锁定版本和权重 |
| [Krita AI Diffusion](https://github.com/Acly/krita-ai-diffusion) | GPL-3.0 | Krita 插件，将 inpaint/outpaint 和提示词工作流接入图层编辑 | 想在人工图层、蒙版和 AI 生成之间快速往返 | 通常需要 ComfyUI/模型后端；硬件、模型许可和网络下载需提前准备 |

IOPaint 是本主题里最接近“完整开源图像修补工具”的方案：官方页面同时覆盖擦除、局部修改和扩图，并提供本地 Web UI、CLI 和 FastAPI 文档入口。它可以把结果接回编辑器的新图层，但最终仍要靠编辑器保留原图、蒙版和每次生成结果。

## 三、按需求选择方案

| 需求 | 首选组合 | 为什么 | 不建议的做法 |
| --- | --- | --- | --- |
| 手工把照片拆成几层并继续设计 | Krita + KRA，或 GIMP + XCF | 图层、蒙版、组、混合模式和撤销完整 | 只保存最终 JPG |
| 在 GIMP 和 Krita 之间交换基础图层 | ORA 作为交换文件，源软件各自保留 XCF/KRA | ORA 是开源交换格式，依赖较少 | 把 PSD 兼容性当作完全一致 |
| 批量添加文字/Logo 水印 | ImageMagick、Pillow 或 libvips | 可脚本化、易部署、无需大模型 | 为固定水印引入扩散模型 |
| Web 端贴纸、文字、图片对象编辑 | Fabric.js 或 Konva + 项目 JSON | 交互对象、变换和序列化成熟 | 只把 Canvas 截图当作项目源文件 |
| 点选前景并导出透明对象 | SAM/SAM 2 + mask 后处理；常见商品图可评估 rembg | 分割与合成职责清晰，可人工修 mask | 期待一次推理准确处理所有发丝和玻璃边缘 |
| 删除人物、文字或背景物体 | 人工 mask + IOPaint/LaMa；简单纹理可用 Resynthesizer | 删除和分层分开，结果可以回退 | 直接覆盖原图，无法比较和重做 |
| 按提示词添加/替换对象 | IOPaint 的扩散模型、Krita AI Diffusion 或 Diffusers/ComfyUI | 支持 mask、提示词和扩图 | 把生成结果覆盖进背景后再继续编辑 |
| 大规模服务端处理 | libvips/ImageMagick + Pillow；AI 作为独立推理服务 | 常规图像处理与 GPU 推理解耦 | 每个请求都启动一次模型或无限并发 |

### 最小可用架构

```text
上传 JPG/PNG
    |
    +--> 保留原图和 EXIF/版权信息
    |
    +--> 解码为 RGBA 工作副本
    |
    +--> 人工选择 / SAM / rembg
    |       `--> mask.png -> 修边、羽化、去色边 -> object.png
    |
    +--> 需要移除？mask.png -> LaMa/IOPaint -> background-repaired.png
    |
    +--> 需要添加？文字/SVG/透明 PNG 或扩散 inpaint -> new-layer.png
    |
    `--> 读取图层 JSON -> 合成预览 -> 保存工程 -> 导出 PNG/JPG
```

Web 产品可以用如下结构保存项目，而不把 Canvas 截图当作唯一源文件：

```json
{
  "canvas": {"width": 2048, "height": 1365, "color": "#ffffff"},
  "layers": [
    {"id": "background", "type": "raster", "src": "background.png", "visible": true},
    {"id": "product", "type": "raster", "src": "product.png", "mask": "product-mask.png", "x": 0, "y": 0, "opacity": 1},
    {"id": "watermark", "type": "svg", "src": "watermark.svg", "x": 1720, "y": 1240, "opacity": 0.55}
  ]
}
```

实际项目还应保存图层顺序、旋转、缩放、混合模式、蒙版版本、生成参数、模型版本和素材来源。AI 结果至少保留原始输入、mask、提示词和生成图，方便审计和重做。

## 四、典型操作示例

### 1. ImageMagick 批量添加透明 Logo 水印

适合已经有 `logo.png` 或 `logo.svg` 的场景。以下命令把 Logo 放在右下角并输出透明 PNG：

```bash
magick input.png logo.png \
  -gravity southeast -geometry +32+32 \
  -compose over -composite watermarked.png
```

对于 JPG 输入，应先决定是否保留 alpha。如果水印不需要透明背景，可以输出 JPG；如果后续还要继续编辑，优先输出 PNG 或保存工程文件，避免反复 JPEG 压缩。

### 2. Pillow 在 Python 中叠加水印

```python
from PIL import Image


def add_watermark(input_path: str, watermark_path: str, output_path: str) -> None:
    """在右下角叠加透明水印；输入和水印保持独立，输出为可继续编辑的 RGBA PNG。"""
    base = Image.open(input_path).convert("RGBA")
    watermark = Image.open(watermark_path).convert("RGBA")
    x = max(0, base.width - watermark.width - 32)
    y = max(0, base.height - watermark.height - 32)
    base.alpha_composite(watermark, dest=(x, y))
    base.save(output_path)


add_watermark("input.jpg", "logo.png", "watermarked.png")
```

生产环境还应限制输入像素总量、校验真实文件类型、处理 EXIF 方向，并在保存前明确颜色空间和输出质量。Pillow 适合把业务规则写进代码，但不会自动给你提供类似 KRA/XCF 的完整图层工程。

### 3. IOPaint/LaMa 进行对象移除

IOPaint 官方安装文档给出的本地启动方式如下：

```bash
pip install iopaint
iopaint start --model=lama --device=cpu --port=8080
```

启动后通过本地 Web UI 或 API 提交原图和黑白 mask。官方 CLI 示例使用图片目录、mask 目录和输出目录进行批处理：

```bash
iopaint run --model=lama --device=cpu \
  --image=/path/to/image_folder \
  --mask=/path/to/mask_folder \
  --output=/path/to/output_folder
```

实操时建议先复制原图作为背景工作层，把修补结果导入为新层；mask 不要删除。大面积天空、墙面、地面等连续纹理可以优先试 LaMa；要按提示词改变或增加内容，再评估扩散 inpainting 模型。

### 4. 用分割 mask 构造透明对象层

```text
SAM/SAM 2 或人工选择
    -> 二值 mask（白色为保留对象）
    -> 对 mask 做闭运算、羽化和人工修边
    -> 原图 alpha = mask
    -> 导出 object.png
    -> 把 object.png 放到 background-repaired.png 上方
```

这里的 `mask` 是核心中间产物：它既可以用于裁剪独立对象，也可以作为 AI 去除区域，还可以作为局部颜色调整或阴影效果的范围。为了避免边缘出现白边/黑边，抠图后要检查对象边缘的颜色去除、羽化半径和目标背景颜色。

## 五、文件格式和工作流建议

### 1. 保存双轨产物

建议始终保存：

- `project.kra` 或 `project.xcf`：主编辑工程；
- `project.ora`：需要在 GIMP/Krita 等开源软件间交换时生成；
- `preview.png`：带透明或无损预览；
- `final.jpg`：只在需要照片交付或兼容旧系统时生成；
- `layers/`：独立 PNG、SVG、mask 和字体/素材记录；
- `project.json`：Web 产品中的位置、变换、顺序和生成参数。

### 2. 不要过早合并图层

以下操作会让后续编辑变得困难：

- 把文字栅格化后再删除原始文字内容；
- 把对象和背景合并后再尝试移动对象；
- 把 mask 应用到唯一副本后再保存；
- 反复打开和保存 JPG；
- 只保存 AI 生成后的图片，不保存 mask、提示词和模型版本。

导出 JPG/PNG 是交付步骤，不是工程保存步骤。若必须交付单张 JPG，也应在内部保留没有合并的源工程和中间层。

### 3. 颜色、透明和元数据

- 统一工作色彩空间，通常先使用 sRGB；印刷或 HDR 场景需要另外规划 ICC/高位深流程。
- JPG 没有 alpha；需要透明对象或透明水印时使用 PNG、WebP 或工程文件。
- PNG 的 RGB 像素可能仍存在于 alpha 为 0 的透明区域，合成时要避免把隐藏颜色误当成可见边缘。
- 导出前处理 EXIF 方向，避免浏览器预览方向和实际像素方向不一致。
- 不要默认删除版权、拍摄信息和来源元数据；按产品隐私和版权策略决定保留或清理。

## 六、许可证和商用风险

“开源方案”至少有三层许可需要分开看：

1. **应用/库代码许可证**：例如 Fabric.js 为 MIT，libvips 为 LGPL-2.1，IOPaint、LaMa、SAM/SAM 2、Diffusers 仓库标注为 Apache-2.0，Krita、ComfyUI 和 Resynthesizer 属于 GPL 系列。
2. **模型和权重许可证**：IOPaint、Diffusers、ComfyUI 只是运行或编排模型的代码；实际使用的 Stable Diffusion、LoRA、ControlNet、U2Net、SAM checkpoint 等要分别阅读模型卡和权重许可。
3. **输入素材和生成内容权利**：原图、Logo、字体、训练素材、人物肖像和水印都可能有独立的版权、商标、隐私或合同约束。

因此，商用部署前应建立第三方清单，记录项目版本、源码许可证、模型/权重许可证、字体和素材来源、是否需要署名、是否允许商用以及是否有地域或用途限制。GPL 组件如果作为独立本地工具使用和作为产品的一部分分发，合规边界也不同，应让法务按实际分发方式确认。

移除他人水印可能侵犯版权或违反平台规则。本文所说的水印移除应限定在图片所有者授权的修图、档案修复、内容审核或内部测试场景；产品功能应考虑权限控制、审计日志和滥用防护。

## 七、最终推荐

### 个人或设计团队

优先安装 Krita 或 GIMP：

- 偏插画、绘画、复杂蒙版和 AI 辅助：Krita + KRA + Krita AI Diffusion；
- 偏照片、批处理、插件和传统合成：GIMP + XCF + Resynthesizer；
- 需要跨软件交换基础图层：额外保留 ORA；
- 需要 AI 移除或扩图：本地 IOPaint，结果以新图层回填。

### Web 图片编辑器

采用“对象画布 + 栅格层 + 项目 JSON”的结构：

- Fabric.js/Konva 管理图片对象、文字、SVG、拖拽和变换；
- PNG 负责透明栅格素材，SVG 负责文字/Logo 等可缩放元素；
- 项目 JSON 保存图层关系和变换，而不是只保存 Canvas 导出的 JPG；
- AI 任务异步执行，原图、mask、结果和模型参数分别保存；
- 服务端使用 libvips/ImageMagick/Pillow 生成最终 PNG/JPG。

### 批量图片处理服务

先做无模型的稳定流水线，再把 AI 作为可选步骤：

```text
文件校验 -> 解码/方向纠正 -> 规则水印/叠加 -> 可选分割 -> 可选修补
    -> 尺寸/颜色/格式处理 -> 输出 -> 记录版本、耗时和失败原因
```

常规水印和合成通常由 ImageMagick、Pillow 或 libvips 完成；只有需要抠图、删除复杂对象、添加语义内容时才调用模型。这样可以控制成本、显存和结果波动，也更容易对每一步做回归测试。
