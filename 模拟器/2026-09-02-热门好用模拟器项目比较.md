# 热门好用模拟器项目比较

## 1. 调研范围与判断口径

- 调研日期：2026-09-02。
- 本文将“模拟器”拆为四类：Android 开发/测试模拟器、Linux 上的 Android 运行环境、游戏主机模拟器、跨架构系统/用户态模拟器。
- “热门”主要参考官方项目活跃度、GitHub Star/Fork、发行节奏和生态成熟度；Star、Fork、Issue 数均为调研时刻快照，不代表质量评分。
- “好用”重点看：目标平台是否匹配、安装门槛、兼容性反馈、图形/输入增强、存档与联机、自动化能力、许可证和长期维护。
- 游戏 ROM、主机 BIOS/固件应由用户从自己合法拥有的设备或软件中导出。本文不提供商业 ROM、BIOS 或绕过版权保护的下载渠道。

## 2. 一句话结论

没有一个模拟器适合所有目标：Android App 开发优先选 Android Studio 自带的 Android Emulator；Linux 桌面想直接运行 Android 应用优先看 Waydroid；复古多主机整合优先选 RetroArch；GameCube/Wii 选 Dolphin；PS2 选 PCSX2；PSP 选 PPSSPP；PS3 只有在接受较高硬件和逐游戏调试成本时才选 RPCS3；跨架构操作系统、固件和用户态程序仿真则选 QEMU。

如果只是想把自己的 Android 手机投屏到电脑或用键鼠控制，不要装模拟器，scrcpy 更合适；它连接真实设备，不负责虚拟出一部 Android 手机。

## 4. Android 模拟器与运行环境

### 4.1 Android Emulator：开发测试的基准答案

Android Emulator 随 Android Studio 和 SDK 提供，不需要把它当作独立的第三方桌面游戏模拟器。官方文档明确将它定位为应用测试工具：通过 Android Virtual Device（AVD）指定 Android 版本、屏幕和硬件配置，每个 AVD 有独立的数据、缓存和 SD 卡空间。

它的优势是官方支持和测试覆盖：可以创建手机、平板、Wear OS、Android TV、折叠设备等配置，并模拟来电、短信、定位、不同网络速度、旋转和传感器。快照可以缩短后续启动时间，命令行和 Gradle/ADB 生态也适合 CI。

资源方面，官方当前建议至少 16GB RAM、64 位 Windows 10 或更高版本，macOS 12 或更高版本，Linux/ChromeOS，以及 16GB 磁盘空间。高 API 版本、大屏设备、多实例和冷启动会进一步增加压力。开发测试不应只依赖模拟器，发布前仍需在真实机上验证厂商 ROM、摄像头、蓝牙、推送、功耗和性能。

**结论：** Android Studio 项目、App 自动化测试和 API/设备矩阵验证优先使用它；如果目标是长时间运行手游或追求更低的游戏输入延迟，应单独评估商业 Android 游戏模拟器或真实设备，而不是把开发模拟器当游戏产品。

### 4.2 Genymotion Desktop：更注重 QA 交互的商业方案

Genymotion Desktop 官方页面列出 40 多个可定制的手机和平板模板，覆盖 Android 5.1 到最新稳定版本，支持 Windows、Linux、macOS，并为 M 系列 Mac 提供 ARM64 镜像。它与 Android Studio 等基于 ADB 的 IDE 兼容，适合测试团队快速切换设备和注入 GPS、相机、媒体、指纹等输入。

需要特别关注授权边界：个人使用有免费版本，但部分高级开发工具、GPS 路线、网络、基带、指纹、游戏手柄等小组件属于 Pro 或其他付费方案。官方还明确说 Genymotion Desktop 设计用于物理工作站，不支持服务器、虚拟机和 VPS；Google Apps 不预装，Play Store 场景需要按官方文档安装 Open GApps。对 ARM-only Android 应用或游戏也要先做兼容性验证。

**结论：** 如果团队重视设备模板、传感器控制和可视化操作，它比原生 AVD 更省 QA 配置时间；如果目标是 Linux 桌面长期运行 Android 应用，Waydroid 更贴近该需求；如果要放进云端 CI，应看 Genymotion SaaS/PaaS 或 Android Emulator 容器方案，而不是直接把 Desktop 部署到 VPS。

### 4.3 Waydroid：Linux 桌面 Android 容器

Waydroid 使用 Linux namespaces 在容器中启动完整 Android 系统，官方仓库说明当前系统镜像基于 LineageOS，README 记录的基础 Android 版本为 Android 13。它不是传统意义上把 ARM 手机硬件逐条软件仿真的模拟器，而是利用 Linux 内核和主机硬件能力运行 Android 用户空间，因此启动快、桌面整合自然。

代价是系统前置条件更明确：官方安装文档要求 Debian/Ubuntu 等发行版启用 Wayland 会话，安装还涉及容器服务、Android 系统/厂商 OTA 镜像和图形驱动。应用是否能正常使用 Google Play、推送、DRM、硬件编解码、相机和 ARM 原生库，取决于镜像和应用本身，不能按“能启动 APK”推断为完整手机兼容。

调研时 GitHub 快照约为 12,093 Star、526 Fork，最新 Release 为 `1.6.3`（2026-05-28）。

**结论：** 它适合 Linux 桌面开发、Android 应用展示、自动化和轻量生产力使用；不适合作为 Windows/macOS 通用 Android 方案，也不宜未经测试就替代真实机做兼容性认证。

## 5. 游戏主机模拟器

### 5.1 RetroArch：多主机统一管理层

RetroArch 本身主要是 libretro 前端，具体系统能力来自可动态加载的核心。官方页面列出 200 多个核心，支持 Windows、macOS、Linux、Android、iOS 等平台。它统一了手柄自动配置、游戏扫描、存档、着色器、成就、网络联机、录制/直播和部分降低输入延迟的能力。

它最适合“很多老主机、希望统一管理”的用户，尤其是 NES、SNES、Mega Drive、街机、GB/GBA、PS1 等复古平台。缺点是核心的实现质量、默认配置和 BIOS 要求各不相同，初次使用时需要理解 Core、Content、System、Save 和 Shader 的目录关系。RetroArch 官网显示的版本、GitHub Release 和不同应用商店版本可能不同，部署时应锁定具体渠道和版本。

**结论：** 多平台收藏库选 RetroArch；单一 3D 主机选专用模拟器，通常更容易获得清晰的逐游戏文档和更少的配置歧义。

### 5.2 Dolphin：GameCube/Wii 的成熟专用方案

Dolphin 官方 README 支持 Windows、Linux、macOS 和近期 Android 设备。当前文档要求桌面 Windows 10 1903 或更高版本、macOS 11 或更高版本；Android 需要 Android 7.0 以上且支持 64 位 ARMv8 或 x86。它的优势包括高清分辨率、纹理和图形增强、逐游戏配置、控制器映射、Motion 输入、网络联机和大量游戏 Wiki 条目。

官方兼容性页面在调研时显示约 67.8% 为 Perfect、30.0% 为 Playable，但这个统计按官方数据库条目计算，不能理解为每个用户在任意硬件上的保证。Dolphin 官方还强调不同游戏可能需要更准确但更耗性能的设置；音频卡顿通常是模拟未达到 full speed 的表现，而不是单纯的音频设备故障。

调研时仓库约 15,472 Star、3,229 Fork；官方网站最新进度文章为 Release 2606（2026-06-25）。Dolphin 的发行渠道和开发构建节奏与 GitHub Release 标签不同，建议从 [官方下载页](https://dolphin-emu.org/download/) 获取构建。

### 5.3 PCSX2：PS2 兼容性与画质增强的平衡

PCSX2 支持 Windows、Linux 和 macOS。官方当前系统要求按 Minimum、Moderate、Heavy 分档：最低档包括 x86-64 SSE4.1、四个物理核心、Vulkan 1.1/Direct3D 11/OpenGL 3.3 和 8GB RAM；Moderate 档建议 AVX2、六个物理核心、Vulkan 1.3/Direct3D 12/OpenGL 4.6、4GB VRAM 和 16GB RAM。

官方特别提醒，性能随游戏差异很大，PS2 BIOS 必须从合法拥有的主机导出。高分辨率、混合和精确渲染设置主要增加 GPU 压力，CPU 密集型游戏则更依赖单线程性能。调研时 GitHub 约 15,464 Star、2,169 Fork；稳定 Release 为 `v2.8.1`（2026-08-30），`v2.9.x` 线存在更新的预发布构建，不宜把预发布版本当成稳定基线。

**结论：** PS2 是本文中“专用模拟器优先”最明显的场景。使用前先检查目标游戏的 PCSX2 Wiki 和兼容性说明，再决定是否启用 2x/3x 以上内部分辨率。

### 5.4 PPSSPP：低门槛 PSP 体验

PPSSPP 是面向 PSP 的快速、跨平台模拟器，官方 README 明确不需要 BIOS，因为它采用 HLE 路线。当前项目覆盖 Android、Windows、macOS、Linux 和 iOS，提供图形分辨率提升、手柄映射、触屏操作、存档状态、纹理替换和多种渲染后端。

它通常比 PS2、PS3 模拟器更容易在手机和低配电脑上达到 full speed，适合移动端和便携设备。仍需注意个别 PSP 游戏的图形后端、帧率补丁、联网和文件访问差异。调研时仓库约 14,373 Star、2,607 Fork，最新稳定 Release 为 `v1.20.4`（2026-05-16）。

**结论：** 如果目标明确是 PSP，PPSSPP 往往是本文最容易安装、最少准备文件、跨设备体验最稳定的一项。

### 5.5 RPCS3：高价值但高门槛的 PS3 方案

RPCS3 是 Windows、Linux、macOS 和 FreeBSD 上的开源 PS3 模拟器/调试器。它持续提供固件安装、逐游戏配置、补丁和兼容性数据库，但项目仍以 Alpha 版本发布。PS3 的复杂 CPU、SPU、图形和系统服务使它对 CPU 单线程性能、AVX 支持、GPU 驱动、内存和 SSD 读取都更敏感，不能用“能打开菜单”代替“可完整游玩”。

调研时仓库约 19,621 Star、2,417 Fork，最新 Release 为 `v0.0.42 Alpha`（2026-07-31）。RPCS3 官方仓库建议通过其网站、Wiki 和兼容性报告判断具体游戏；目标游戏没有成功报告时，应预留调试和回归成本。

**结论：** RPCS3 适合愿意按游戏逐项调参的高级用户和开发者，不适合要求“一键全库稳定运行”的场景。不要因为 Star 数高就把它排在 Dolphin、PCSX2 或 PPSSPP 之前。

### 5.6 melonDS：DS 双屏和触控场景

melonDS 专注 Nintendo DS/DSi，官方 README 说明目标是正确且快速地完成 DS 仿真，并支持 Windows、Linux、macOS 和 BSD 方向的构建。原始 DS/DS Lite 的 BIOS/固件文件需要从设备中合法导出；DSi/3DS 的 DS 模式固件并不能在所有启动模式下替代原始固件。

它的项目规模小于前几项，DSi 仿真、图形和网络等方向仍在持续完善。调研时仓库约 4,981 Star、813 Fork，最新 Release 为 `1.1`（2025-11-18）。

**结论：** 需要 DS 双屏、触控和专门的 DS 工作流时选 melonDS；只想在一个前端里顺手运行少量 DS 游戏时，也可以比较 RetroArch 的对应核心。

## 6. QEMU：系统和跨架构仿真

QEMU 的范围比游戏模拟器大得多。官方将能力分为三块：完整机器仿真、用户态仿真和虚拟化。完整系统仿真可以在不同主机架构上运行目标机器的操作系统；用户态仿真可以运行面向另一种 Linux/BSD ABI 编译的程序；在 KVM/Xen 可用时，还可以用接近原生的速度运行虚拟机。

因此 QEMU 适合固件启动测试、嵌入式板卡开发、ARM/RISC-V/x86 交叉验证、内核和驱动测试、系统镜像构建，以及需要隔离的 CI。它不是替代 Dolphin/PCSX2 的游戏软件，使用体验取决于机器模型、固件、磁盘镜像、网络和加速配置。QEMU 整体采用 GPLv2，但随发行版提供的固件和其他组件可能有独立许可证，分发时要逐项核查。

调研时仓库约 13,666 Star、7,135 Fork；官方仓库说明 GitHub 是镜像，提交和发布应以 QEMU 官网与上游项目流程为准。

## 7. 常被混淆的相关项目

### scrcpy：真实 Android 设备控制工具，不是模拟器

scrcpy 通过 USB 或 TCP/IP 镜像并控制真实 Android 设备，支持 Linux、Windows 和 macOS，不需要 root 或在手机安装常驻 App。它提供录屏、音频转发、键鼠控制、虚拟显示、摄像头转发和 OTG 等能力。调研时 GitHub 约 148,716 Star、13,675 Fork，Apache-2.0 许可证，热度明显高于本文多数模拟器项目。

它适合真机调试、演示、自动化前置和低延迟控制；但它不提供虚拟 Android 版本、虚拟传感器、虚拟 IMEI 或隔离的数据盘。需要模拟设备矩阵时仍应使用 Android Emulator、Genymotion 或云真机。

### 不作为新项目首选的方案

- AetherSX2 项目本身已经停止作为活跃上游维护，且存在大量非官方镜像和冒名下载页面，不建议把它作为新的长期依赖。
- Yuzu、Citra 等项目曾经很热门，但原始上游已不再是稳定的持续维护选择；不要只按旧文章中的性能评价或下载链接部署。
- BlueStacks、LDPlayer、MuMu 等闭源 Android 游戏运行器可能更适合特定手游和键位需求，但其版本、广告/账号、隐私、商业授权和游戏反作弊兼容性需要单独核查。本文以可复核的官方文档和开源项目为主，没有把它们与开源模拟器按同一指标打分。

## 8. 按目标落地的推荐组合

| 目标 | 推荐组合 | 原因 |
| --- | --- | --- |
| Android App 开发与 CI | Android Emulator + ADB/Gradle；必要时加入真实设备 | 官方 API/AVD 适配最好，便于设备矩阵和自动化；真实机补足厂商差异 |
| Android QA 多设备交互 | Genymotion Desktop 或 Genymotion SaaS/PaaS + Android Emulator | Genymotion 传感器和设备模板易用，云端场景不要直接部署 Desktop 到 VPS |
| Linux 桌面运行 Android 应用 | Waydroid；问题应用用 Android Emulator 或真机复测 | Waydroid 与桌面整合好，但受 Wayland、镜像、驱动和 Google 服务影响 |
| 复古多主机收藏库 | RetroArch；对单一平台再叠加专用模拟器 | 统一核心、手柄、着色器、存档和联机设置；专用模拟器用于疑难游戏 |
| GameCube/Wii | Dolphin | 专项文档、兼容性数据库和图形增强更完整 |
| PS2 | PCSX2 | 成熟度和逐游戏资料较好，但准备合法 BIOS 并按游戏验证 |
| PSP | PPSSPP | 跨平台、无需 BIOS、硬件门槛低 |
| PS3 | RPCS3 | 目标游戏先查兼容性报告，准备高性能 CPU、驱动和调参时间 |
| 固件/跨架构/嵌入式 | QEMU | 完整系统和用户态仿真能力最广，适合工程验证而不是游戏体验 |
| 真机投屏和控制 | scrcpy + 真实 Android 设备 | 延迟低、无须安装常驻 App；不占用虚拟设备资源 |

## 9. 部署与验收建议

1. 先固定“目标平台 + 目标软件/游戏 + 主机系统”，不要从“哪个模拟器 Star 多”开始选。
2. 先用官方稳定版验证启动、输入、音频、存档、分辨率和退出恢复，再考虑 nightly、预发布版、图形补丁和纹理包。
3. Android 场景至少验证 ARM 原生库、Google 服务、推送、相机、蓝牙、定位、DRM 和后台限制；模拟器通过不代表真实设备通过。
4. 游戏场景按目标游戏建立兼容性清单，记录模拟器版本、图形后端、分辨率、补丁、BIOS/固件和存档格式，避免升级后无法复现。
5. CI 场景优先用可脚本化的 ADB、快照、容器或云设备能力，并单独测量冷启动、并发数、磁盘 I/O、视频编码和失败恢复。
6. 对商业软件确认个人/教育/企业授权、离线使用期限、账号依赖和数据收集；对开源软件逐项阅读主程序、核心、固件和资源包的许可证。
