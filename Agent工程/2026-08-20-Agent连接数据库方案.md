# Agent 连接数据库方案调研

> 调研日期：2026-08-20。本文关注让 Agent 查询、分析或操作结构化数据库的工程方案，资料以 MCP、OpenAI Agents SDK、Microsoft Data API builder、Google MCP Toolbox、LangChain、LlamaIndex 以及 Neon/Supabase 官方文档和仓库为主。产品能力、协议版本和仓库状态会变化，正式上线前应按目标版本复核。

## 结论

Agent 连接数据库不是“给模型一条数据库连接串”这么简单，而是四层问题：

1. **连接协议**：Agent 如何发现和调用工具，MCP、SDK 内置工具或普通 HTTP API 都可以。
2. **工具契约**：暴露原始 SQL、实体 CRUD、领域动作，还是指标查询接口。
3. **权限与策略**：谁能访问哪些表、行、列和动作，租户身份由谁注入，哪些调用需要审批。
4. **执行环境**：生产主库、只读副本、数仓、沙箱数据库或临时分支。

推荐的生产基线是：

> **Agent 编排器 + 身份/策略网关 + 领域工具或语义层 + 只读副本/受控数据库角色**，MCP 作为可选的标准化工具连接层；原始 `execute_sql` 只用于受控的开发或分析场景，默认只读。

不要让终端用户 Agent 直接持有生产管理员账号，也不要把“请只查询、不修改数据”写在系统提示词里就当成安全控制。模型生成的 SQL 和租户过滤条件都必须经过后端策略、数据库权限和必要的人工审批。

## 一、先区分四类需求

| 需求 | 主要问题 | 更合适的接口 |
|---|---|---|
| 开发 Agent 查看本地数据库、生成代码 | 需要快速发现表结构和运行查询 | 本地 MCP 或 SDK + 只读开发库 |
| 业务用户用自然语言查报表 | 指标口径、租户隔离和结果准确性 | 语义层、预定义查询工具、数仓/只读副本 |
| Agent 执行订单、退款、审批等业务动作 | 业务规则、幂等、审批和审计 | 领域 API、存储过程或实体 CRUD 工具 |
| Agent 管理数据库、迁移 schema | 破坏性操作和回滚 | 厂商管理 MCP + 分支/沙箱 + 显式审批 |

“查数据”和“改数据”不应共用一套默认工具。前者可以在严格限制后自动运行，后者应先生成计划或变更，再验证、审批和提交。

## 二、方案横向比较

| 方案 | Agent 看到的内容 | 优点 | 主要风险或代价 | 推荐场景 |
|---|---|---|---|---|
| 应用内置驱动与工具函数 | 应用自己定义的函数，函数内部调用数据库驱动 | 延迟低、控制最细、容易复用现有认证和业务逻辑 | 只能被当前应用使用，需要自行维护工具协议和工具描述 | 单一产品、业务写操作、对安全要求高 |
| 通用 SQL Agent | 表结构、SQL 生成和查询执行工具 | 原型快，能回答开放式问题 | SQL 幻觉、越权、笛卡尔积、慢查询和敏感数据外泄 | 内部分析、开发库、只读副本、概念验证 |
| MCP 通用数据库服务器 | `tools/list` 暴露的 schema、查询或 CRUD 工具 | 客户端兼容面广，Agent 和数据库服务可独立部署 | MCP 只规定工具调用，不自动提供数据库权限；通用 `execute_sql` 风险高 | 多 Agent/多 IDE 接入、开发工具链 |
| MCP Toolbox / 自建 MCP 领域工具 | 预置数据库工具或定制的参数化业务工具 | 可以同时支持多种数据库；工具可限制参数、SQL、工具集和数据源 | 需要维护配置、发布、认证和版本；预置 SQL 工具仍需治理 | 通用平台、企业数据访问、生产查询 |
| 语义层或领域 API | 指标、实体和业务动作，不直接暴露底层表 | 口径稳定、权限容易绑定、最适合多租户和写操作 | 前期建模成本高，覆盖开放式探索的能力有限 | 面向终端用户的生产系统 |
| 数据库厂商托管 MCP | 厂商项目、分支、SQL、迁移等管理工具 | 登录和运维集成快，通常有厂商特有能力 | 权限经常覆盖整个项目；工具可能同时支持读写和 DDL，供应商耦合明显 | 开发/运维 Agent、个人项目、临时分支 |

这里的“方案”可以组合：例如使用 MCP 作为传输协议，通过 MCP Toolbox 暴露语义层工具，工具内部再调用数仓；或者用 LangChain/LlamaIndex 编排一个只读 SQL Agent，但不把框架本身当成安全边界。

## 三、代表实现与适用边界

### 1. MCP：标准化工具连接层

当前 MCP 工具规范通过 `tools/list` 发现工具，通过 `tools/call` 调用工具，并使用 JSON Schema 描述输入和可选的结构化输出。数据库 Agent 可以因此获得类似以下工具：

- `describe_customer`：读取受控的客户实体；
- `list_orders`：按固定参数查询订单；
- `aggregate_sales`：调用预定义的聚合查询；
- `prepare_migration` / `apply_migration`：拆分高风险变更的准备和提交。

MCP 规范明确把工具设计为模型可控制的调用，同时建议敏感操作保留能够拒绝调用的人在回路中。规范还要求服务器验证工具输入、实施访问控制、限流和输出清洗；客户端应考虑确认提示、结果校验、超时和审计日志。工具描述和工具注解不能替代服务端授权，客户端也不应无条件信任不可信服务器返回的工具注解。

OpenAI Agents SDK 当前支持托管 MCP、Streamable HTTP、SSE 和 stdio 等连接方式，并提供工具过滤、工具名冲突处理和审批回调。这样可以把“Agent 如何连接”与“数据库工具如何授权”解耦，但仍需由应用自己选择可信服务器、最小权限凭据和敏感操作审批策略。

**判断**：MCP 适合解决跨 Agent、跨 IDE 和跨应用的工具复用；它不是数据库代理、SQL 防火墙或权限系统。是否安全取决于 MCP Server 暴露的工具面、服务端身份和下游数据库权限。

### 2. Microsoft SQL MCP Server / Data API builder：实体化 CRUD

Microsoft 的 SQL MCP Server 建立在开源 Data API builder（DAB）之上。DAB 用配置文件定义数据库连接、表/视图/存储过程和权限，并可同时暴露 REST、GraphQL 和 MCP。MCP 侧的核心思路是让 Agent 访问配置中的实体，而不是直接接触数据库。

当前 DAB 源码中的 DML 工具包括实体描述、读取、创建、更新、删除、执行实体和聚合等能力；运行时和实体级配置都可以逐项关闭工具。DAB 还复用实体权限、角色和字段投影等 API 能力。

适合：

- 已经使用 SQL Server、Azure SQL、PostgreSQL 或 MySQL，并希望复用 API 权限模型；
- 业务 Agent 需要实体级 CRUD，而不是任意 SQL；
- 希望让 REST、GraphQL 和 MCP 共用一份对象配置。

注意：DAB 的 DML 工具默认配置可能是全开，生产环境应显式关闭删除、更新、创建和不需要的执行工具，只给 Agent 暴露白名单实体。若需要给用户做多租户查询，还必须在数据库 RLS、DAB 策略或后端身份注入层实现租户隔离，不能依赖 Agent 自己记住过滤条件。

### 3. Google MCP Toolbox：预置工具与定制工具框架

MCP Toolbox for Databases 是 Google 开源的数据库 MCP Server，仓库已从 `genai-toolbox` 更名为 `mcp-toolbox`。它有两个层次：

- **预置工具**：例如列出表、读取 schema、执行 SQL，适合开发和数据探索；支持 PostgreSQL、MySQL、SQL Server、Oracle、MongoDB、Redis、BigQuery、Cloud SQL、Spanner、Snowflake 等多种数据源。
- **定制工具**：通过 `tools.yaml` 定义数据源、参数化 SQL、工具描述、工具集和提示词，支持结构化查询、语义搜索和 NL2SQL 组合。

项目还把连接池、部分 IAM 认证和 OpenTelemetry 可观测性作为内置能力。它的生产价值主要在“定制工具框架”，不是把预置 `execute_sql` 原样开放给终端用户。

适合：

- 需要让多个 Agent 客户端复用一套数据库工具；
- 希望通过配置文件集中维护数据源和工具白名单；
- 既要快速探索，又要逐步沉淀领域查询工具。

落地时建议先按业务建立少量定制工具，例如 `query_monthly_sales`、`lookup_order_status`，参数只暴露日期、状态、分页等业务参数；租户、用户和权限由服务端或数据库会话注入，不让模型传入任意 `tenant_id`。

### 4. LangChain SQL Agent：完整的 Text-to-SQL 编排样例

LangChain 的 `SQLDatabaseToolkit` 提供了列出表、查看 schema/样例行、执行 SQL 和检查 SQL 的工具。官方 SQL Agent 教程的典型流程是：

1. 获取可用表和 schema；
2. 判断与问题相关的表；
3. 生成 SQL；
4. 通过另一个模型检查常见错误；
5. 执行 SQL，并把数据库错误反馈给模型重试；
6. 根据结果组织回答。

官方教程同时明确提示，示例中的数据库工具只是演示用的最小封装，不应直接作为生产安全方案；应使用尽可能窄的数据库权限，并在执行模型生成的 SQL 前增加应用级校验。教程还演示了在执行查询前暂停等待人工审核。

适合：只读分析原型、内部数据助手、需要自定义 Agent 循环和错误修复的项目。

不适合直接承担：生产权限隔离、多租户强约束、订单写入、schema 迁移和合规审计。LangChain/LangGraph 负责编排和暂停恢复，真正的授权仍需在工具服务和数据库层完成。

### 5. LlamaIndex Text-to-SQL：schema 检索与查询引擎

LlamaIndex 提供 `NLSQLTableQueryEngine` 和 `SQLTableRetrieverQueryEngine`。前者可指定允许参与查询的表，后者可以先检索相关表 schema，再生成 SQL，适合数据库表很多、不能把全量 schema 放进上下文的情况。

官方结构化数据指南明确警告，执行任意 SQL 存在安全风险，建议使用受限角色、只读数据库或沙箱。源码也提供 `sql_only` 等能力，使应用可以先展示或评估 SQL，再决定是否执行。

适合：schema 较多的分析问答、需要把表描述和业务术语加入检索上下文的项目。它的关键能力是上下文选择和查询编排，不是自动得到正确的权限模型。

### 6. Neon、Supabase 等厂商 MCP：开发和平台运维优先

厂商 MCP 的便利性最高，但通常权限范围也更大：

- **Neon MCP** 提供项目、分支、表结构和 SQL 工具，`run_sql` 同时支持读写，并提供事务、数据库迁移和临时分支。迁移可以先在临时分支准备和测试，再提交到主分支，这适合开发 Agent 和数据库运维 Agent；但不应把整个账号级工具集直接交给终端用户 Agent。
- **Supabase MCP** 提供远程 OAuth MCP，也支持按项目限定、按 feature group 筛选以及 `read_only=true`。其官方仓库明确要求先阅读安全最佳实践；本地 CLI 和自托管环境的工具集合又与云端不同，部署前要核对实际能力。

这类方案适合开发者说“创建一个分支”“查看 schema”“在测试库执行迁移”。面向业务用户查询订单或客户数据时，仍应使用自己的领域 API、RLS 和只读工具，而不是把厂商管理 MCP 当作数据访问层。

## 四、推荐的生产架构

```text
用户请求
   |
   v
Agent 编排器（意图识别、计划、重试、上下文）
   |
   +--> 工具注册表/风险策略
   |       |- 低风险：指标查询、实体读取、聚合
   |       |- 中风险：受限只读 SQL
   |       `- 高风险：准备变更、申请审批、提交变更
   |
   v
身份与策略网关
   |- 从登录会话注入 user_id、tenant_id、角色
   |- 工具白名单、参数校验、行数/超时/成本限制
   |- PII 脱敏、审计、审批和幂等控制
   |
   v
领域工具 / 语义层 / MCP Server
   |- 预定义 SQL、视图、存储过程或业务 API
   `- 仅在受控场景暴露 Text-to-SQL
   |
   +--> 数仓或只读副本（分析）
   +--> 业务库受限角色（实体读取）
   `--> 分支/沙箱数据库（迁移和测试）
```

### 推荐的默认工具分层

| 风险级别 | 示例 | 默认策略 |
|---|---|---|
| 低 | `get_order_status`、`aggregate_sales`、`list_allowed_products` | 可自动执行，但仍做身份、参数和结果限制 |
| 中 | `read_records`、受限 `read_sql` | 只读角色、表/视图白名单、单语句、超时和最大返回行数 |
| 高 | `update_order`、`refund_order`、`run_sql` 写操作 | 事务、幂等键、影响行数预览、人工或业务审批 |
| 极高 | `drop_table`、`grant`、生产迁移、导出全量 PII | 不暴露给普通 Agent；通过专用运维流程和双人审批 |

## 五、安全基线

### 1. 身份和租户隔离

- 用户身份和租户身份必须从可信会话、网关或服务端上下文取得，不能由模型自由填写。
- 在数据库使用 RLS、专用 schema、视图或存储过程再次约束访问；应用层过滤只是额外一层。
- 多租户场景不要只提供一个通用 `execute_sql`。Google Cloud 的 MCP 安全指南明确指出，恶意输入可能诱导 Agent 查询其他用户数据；更安全的做法是提供 `lookup_active_order` 这类由后端固定用户条件的定制工具。

### 2. 最小权限和环境隔离

- 为每种 Agent、环境和风险等级配置独立数据库角色或服务账号。
- 分析 Agent 默认连接只读副本或数仓；写 Agent 使用独立写权限，并禁止 DDL、授权和系统表访问。
- 迁移 Agent 先操作临时分支或沙箱，验证差异、测试和回滚路径后才允许提交。
- 密钥放在 Secret Manager、环境变量或授权头中，不要放进 MCP URL、提示词或仓库；OpenAI Agents SDK 也建议把访问令牌放在授权字段/请求头中。

### 3. 工具和 SQL 限制

- 首选参数化领域工具、受控视图和存储过程；只把业务参数暴露给模型。
- 如果必须支持 SQL，使用数据库只读角色，加 SQL AST/方言校验，拒绝多语句、DDL、DML、注释绕过、系统表和危险函数，并设置超时、最大行数、分页和成本阈值。
- SQL 解析器不是权限边界，最终仍要靠数据库角色、RLS 和资源限制兜底。
- 不要把全部 schema、样例行和敏感列一次性放进上下文；先按意图选择表或指标，并对 schema 和样例数据做脱敏。

### 4. 写入、审批和可恢复性

- 对更新、删除、退款、发送消息和迁移等操作，先生成结构化计划或预览，展示工具名、参数、SQL 摘要、影响范围和预计行数。
- 使用人审、业务规则或二次策略模型审批高风险调用；审批不能只发生在 UI，服务端也必须重新校验。
- 写操作使用幂等键、事务、乐观锁和回滚/补偿流程。禁止把“模型说执行成功”当作数据库提交事实。

### 5. 数据外发和审计

- 对 PII、密钥、支付信息和内部凭证做列级屏蔽、结果脱敏和输出长度限制。
- 记录用户、租户、会话、Agent、工具版本、工具参数、实际 SQL 或查询哈希、审批结果、数据库、行数、耗时、错误和结果摘要。
- 同时开启应用工具日志和数据库审计日志；日志本身也要脱敏，避免把完整查询结果写入普通日志。
- 对 Agent 做回归测试：越权表访问、跨租户查询、提示词注入、危险 SQL、慢查询、超大结果集、重复提交和数据库错误诱导重试。

## 六、按场景选型

| 场景 | 首选组合 | 不建议 |
|---|---|---|
| 本地开发 Agent + SQLite/PostgreSQL | 本地 stdio MCP 或 LangChain/LlamaIndex + 测试库 | 连接生产库，或给模型管理员权限 |
| 企业内部自然语言报表 | 语义层/指标模型 + 定制 MCP 工具 + 数仓/只读副本 | 直接把全库 schema 和 `execute_sql` 暴露给所有用户 |
| 多租户 SaaS 数据助手 | 领域 API/定制工具 + 服务端身份注入 + RLS | 让模型传 `tenant_id`，再靠提示词要求它过滤 |
| 订单、审批、客服操作 Agent | 领域 API/存储过程 + 幂等 + 审批 | 用 Text-to-SQL 直接更新业务表 |
| Microsoft 数据栈 | DAB 实体 MCP，按实体和角色配置 | 默认开启全部 DML 工具 |
| 多数据库、多个 Agent 客户端 | MCP Toolbox 定制工具或自建 MCP Server | 只使用预置通用 `execute_sql` 作为生产接口 |
| Neon/Supabase 开发运维 | 厂商 MCP + 项目限定 + 只读/分支 + 人审 | 把账号级项目管理和写 SQL 工具交给终端用户 |

## 七、建议的落地顺序

1. **盘点数据面**：列出数据库、表、视图、敏感列、租户字段、读写动作和数据保留要求。
2. **先建安全数据面**：创建只读角色、只读副本或数仓视图；补齐 RLS、字段脱敏和查询超时。
3. **先做 5 至 10 个定制工具**：从高频、低风险问题开始，工具参数只表达业务意图，不暴露表名和任意 SQL。
4. **选择连接层**：单应用优先应用内置工具；需要多客户端再接 MCP；跨数据库可评估 MCP Toolbox；Microsoft 数据栈可评估 DAB。
5. **单独设计写入流**：写操作分为准备、验证、审批、提交四步，使用独立工具和数据库角色。
6. **加入可观测性和评测集**：同时测答案准确率、SQL 正确率、权限边界、延迟、成本、审计完整性和故障恢复。
7. **逐步开放原始 SQL**：只有当定制工具无法覆盖确有价值的探索需求时，才向受信任的内部用户开放受限只读 SQL。

## 最终建议

如果要建设一个通用的 Agent 数据访问平台，建议采用：

> **定制领域工具/语义层作为主入口，MCP Toolbox 或自建 MCP Server 作为标准连接层，LangGraph/OpenAI Agents SDK 负责编排与审批，数据库 RLS/只读角色/审计负责最终约束。**

如果只是快速验证自然语言查数，使用 LangChain 或 LlamaIndex 连接只读副本即可；如果目标是生产业务 Agent，则应优先建设领域 API、语义层和权限模型，而不是继续扩大原始 SQL 工具的能力。
