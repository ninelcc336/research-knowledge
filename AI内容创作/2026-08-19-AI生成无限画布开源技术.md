# AI生成产品的无限画布开源技术调研

## 1. 调研范围

- 调研日期：2026-08-19。
- 目标：为已有产品增加一个可以放置提示词、参考素材、生成结果和处理节点的无限画布，支持文生图、图生图、文生视频、图生视频，并保留可复用的工作流。
- 重点核查：画布交互和渲染、节点连接、持久化与协作、图片/视频生成后端、异步任务、媒体处理、许可证。
- 资料来源：项目官方 README、LICENSE、官方文档、GitHub 仓库元数据和关键源码。GitHub Star 等动态指标不作为稳定结论；模型权重、第三方节点和外部 API 的许可证需要单独复核。

## 2. 一句话结论

对一个商业 Web 产品，前端应先按现有技术栈选画布层，后端保持跨框架复用：

> **React 选 `@xyflow/react`，Vue 选 Vue Flow，原生 Web 选 Drawflow 或 LiteGraph.js；节点内部渲染图片/视频/参数面板，后端统一通过 Provider Gateway 接入托管模型 API、InvokeAI、ComfyUI 或 Diffusers，协作后置到 Yjs + Hocuspocus。**

如果产品的核心是“自由摆放和编辑素材”，而不是连接生成依赖，则三个技术栈都可以使用 Fabric.js 或 Konva；需要高吞吐特效时再考虑 PixiJS。tldraw 当前 SDK 主要面向 React，并且生产环境需要许可证密钥和商业授权条件。ComfyUI 的能力最完整，但仓库和官方前端均为 GPL-3.0，不应在闭源商业产品中未经许可证评估直接嵌入。

## 3. 先确定产品形态

| 产品形态 | 用户主要操作 | 更合适的技术方向 | 主要代价 |
| --- | --- | --- | --- |
| 灵感板/素材板 | 摆放图片、视频、文字、参考图，调整大小和层级 | Fabric.js、Konva；或商业授权的 tldraw | 需要自己实现生成依赖、节点端口和执行状态 |
| 节点式生成工作流 | 连接文本、图片、模型、编辑和输出，按依赖执行 | React Flow、Vue Flow、Drawflow、LiteGraph.js 或 Rete | 需要自己补充自由画布对象、媒体编辑和高性能预览 |
| 混合创作工作区 | 既要自由摆放，又要把素材连成图像/视频工作流 | 对应技术栈的节点库 + Fabric/Konva 局部编辑器 | 两套对象模型和坐标系统需要明确边界 |
| 本地工作站 | 用户在桌面端保存模型、密钥和媒体，离线生成 | 对应技术栈的画布 + Tauri + ComfyUI/InvokeAI | 桌面打包、GPU、模型下载和跨平台运维成本较高 |

本调研默认目标是第三种“混合创作工作区”，但建议第一版先收敛为节点式工作流，避免同时建设两个完整编辑器。

## 4. 按前端技术栈拆分

本节的“原生”指不依赖 React/Vue 的浏览器方案，主要使用 DOM、Canvas 2D、SVG 或 WebGL/WebGPU。三种技术栈都可以复用后面的生成后端、任务队列、媒体存储和协作层。

**Vue 推荐组合：**Vue Flow + Pinia；需要像素/图层编辑时增加 Vue Konva；如果未来还要支持 React 或希望把图执行引擎独立出来，优先评估 Rete.js。

### 4.3 原生 Web/Vanilla JS 模块

| 项目 | 定位与能力 | 许可证 | 适用判断 |
| --- | --- | --- | --- |
| [Drawflow](https://github.com/jerosoler/Drawflow) | 无依赖的 JavaScript 流程库，支持多输入/输出、多连接、重连、缩放、模块、事件、导入导出和移动端；也支持 Vue 节点 | MIT | **原生节点画布最容易上手**。适合轻量工作流和产品原型；当前默认分支主要提交较早，长期维护和 TypeScript 类型需要自行评估。 |
| [LiteGraph.js](https://github.com/jagenjo/litegraph.js) | Canvas 2D 节点图编辑器，支持平移缩放、多选、快捷键、上下文菜单、子图、自定义节点、JSON 导出和 Node.js 执行；ComfyUI README 将其列为项目使用者 | MIT | 适合需要 Canvas 节点渲染、子图和 ComfyUI 风格的原生产品。仓库近年核心提交较少，使用前应锁定版本并准备维护分支。 |
| [Fabric.js](https://github.com/fabricjs/fabric.js) | 框架无关的 2D 对象模型，支持选择、移动、旋转、缩放、分组、图片滤镜、画笔和 JSON/SVG/JPG/PNG 导入导出 | MIT | **原生自由素材画布首选之一**。适合灵感板和媒体对象布局；不提供工作流图和任务执行。 |
| [Konva](https://github.com/konvajs/konva) | 框架无关的 Canvas 2D 场景图、Layer、事件、命中检测、移动和变换 | MIT（以仓库 LICENSE 为准） | 适合中等规模的图片、蒙版、图形和时间轴预览；比直接操作 Canvas 更易维护，但对象协议和历史需要自建。 |
| [PixiJS](https://github.com/pixijs/pixijs) | WebGL/WebGPU 2D 渲染、纹理、滤镜、遮罩和高吞吐精灵 | MIT | 适合大量媒体缩略图、复杂特效或高帧率场景。它是渲染引擎而不是编辑器，实施成本最高。 |

**原生推荐组合：**节点式工作流优先 Drawflow；如果必须兼容 ComfyUI 风格和子图，评估 LiteGraph.js；自由素材板使用 Fabric.js 或 Konva，性能瓶颈明确后再上 PixiJS。

### 4.4 跨框架公共能力

- [Rete.js](https://retejs.org/docs) 是最适合跨 React/Vue/Angular/Svelte/Lit 共享图模型的候选，既有可视化插件，也有 dataflow/control flow 引擎；代价是插件组合和学习成本更高。
- Fabric.js、Konva、PixiJS 的核心不依赖 React 或 Vue，可以把渲染层包进不同技术栈，但不能因此自动获得节点连接、权限、协作或任务状态。
- [Yjs](https://github.com/yjs/yjs) + [Hocuspocus](https://github.com/ueberdosis/hocuspocus) 是协作层而不是画布层。它们可以同步任意技术栈的节点文档；媒体二进制不能直接塞进 CRDT，应只同步 asset ID、URL、版本和元数据。
- React Flow、Vue Flow、Drawflow、LiteGraph.js 都需要自行定义生成节点的数据协议；不要把具体模型参数和画布组件强耦合。

### 4.5 三种技术栈快速对比

| 维度 | React | Vue | 原生 Web |
| --- | --- | --- | --- |
| 节点工作流 | React Flow 最成熟；Rete 适合复杂执行 | Vue Flow 上手快；Rete Vue 适合跨框架 | Drawflow 简单；LiteGraph.js 更接近 ComfyUI |
| 自由素材画布 | React Konva、Fabric.js | Vue Konva、Fabric.js | Fabric.js、Konva、PixiJS |
| 组件生态 | 最丰富，完整 AI 画布参考项目较多 | 基础库完整，但 AI 画布成品参考较少 | 依赖少、控制力强，但交互和状态要自建 |
| 性能控制 | DOM/Canvas 混合方便，需控制 React 重渲染 | 响应式更新直观，需控制深层对象追踪 | 控制最直接，工程复杂度最高 |
| 适合团队 | React 已有产品或需要快速招人 | Vue 3 已有产品、偏业务化团队 | 需要轻量嵌入、桌面 WebView 或不想引入 UI 框架 |

### 4.6 画布选型判断

- 不要为了画布迁移已有前端框架：已有 React 就选 React Flow，已有 Vue 3 就选 Vue Flow，原生项目优先 Drawflow/LiteGraph.js。
- 需要“卡片自由排列 + 生成结果继续作为输入”时，节点库可以把媒体卡片实现为自定义节点；先不要引入第二套完整画布。
- 需要画笔、蒙版、旋转、裁切和多层合成时，在生成工作流之外增加 Fabric/Konva 局部编辑器；不要让生成 DAG 和像素编辑层共用一套不可迁移的状态字段。
- 需要多人协作时，同步文档状态和操作，不同步大文件；上传、缩略图和视频转码走独立的对象存储与媒体服务。

### 5.1 ComfyUI 与 InvokeAI 的取舍

- 选择 ComfyUI：需要最大化模型/节点兼容性、允许独立 GPU 服务、可以接受 GPL 合规审查，并且愿意自己维护 workflow 模板和版本兼容。
- 选择 InvokeAI：希望使用 Apache-2.0 的基础、需要已有 Canvas/图库/工作流/API、主要关注产品交付而不是接入所有社区节点。
- 选择 Diffusers：已有推理平台和 GPU 工程能力，或需要对模型加载、批处理、显存隔离、计费和服务协议进行完全控制。
- 选择托管 API：产品还在验证阶段，不希望自建 GPU；此时开源技术重点放在画布、任务状态、Provider 接口、媒体存储和可替换性，而不是本地推理。

## 7. 推荐的产品架构

### 7.1 前端

前端画布层按现有技术栈选择，不建议为了使用某个库而迁移整个产品：

| 现有技术栈 | 节点工作流层 | 自由素材/像素层 | 状态管理建议 |
| --- | --- | --- | --- |
| React | React Flow；复杂图执行可评估 Rete React 插件 | React Konva、Fabric.js | Zustand 或现有 React 状态方案 |
| Vue 3 | Vue Flow；跨框架或复杂图执行可评估 Rete Vue 插件 | Vue Konva、Fabric.js | Pinia 或现有 Vue 状态方案 |
| 原生 Web | Drawflow；ComfyUI 风格或子图需求可评估 LiteGraph.js | Fabric.js、Konva；高吞吐场景再用 PixiJS | 轻量自定义 store，或把文档交给 Yjs |

无论使用哪种技术栈，都应使用一个画布文档作为业务事实来源：

- `TextPromptNode`：提示词、负面提示词、变量和风格片段。
- `AssetNode`：上传图、参考图、已生成图片、视频、音频和封面。
- `ImageGenerateNode`：文生图、图生图、编辑、局部重绘、放大。
- `VideoGenerateNode`：文生视频、图生视频、首尾帧、视频延长。
- `ProcessNode`：抽帧、裁切、蒙版、拼接、转码、字幕和音频处理。
- `OutputNode`：结果选择、对比、下载、再次作为输入。

每个节点只保存参数和 asset/job 引用，不把大文件 Base64 放进画布 JSON。生成结果应创建新的资产版本或新节点，保留输入、提示词、模型、seed、尺寸、时长和 Provider 响应，才能支持复现、重试和历史对比。

### 7.2 服务端

建议拆成以下边界：

```text
浏览器画布
  -> Canvas API（文档、权限、版本、资产引用）
  -> Generation Gateway（统一参数、鉴权、额度、Provider 路由）
  -> Job Queue（提交、轮询、取消、重试、幂等）
  -> ComfyUI / InvokeAI / Diffusers / 托管 API
  -> Media Worker（FFmpeg、缩略图、封面、代理文件、元数据）
  -> 对象存储 + 数据库
```

- Node.js 产品可以用 [BullMQ](https://github.com/taskforcesh/bullmq) 做初期异步队列；如果任务需要长时间运行、跨服务补偿和复杂重试，可评估 [Temporal](https://github.com/temporalio/temporal)。
- Provider 接口至少统一 `submit`、`getStatus`、`cancel`、`getOutputs`，不要让前端节点直接调用模型厂商。
- 每次任务生成 `job_id`、`request_hash` 和 `provider_job_id`，用 request hash 防止用户重复点击产生重复扣费。
- 生成状态放服务端，前端用 WebSocket/SSE 或短轮询订阅；页面关闭后任务仍应继续，重开画布可恢复。
- 图片和视频放对象存储，数据库只保存 asset、版本、媒体尺寸、时长、封面、来源和权限。生产环境要限制远程 URL 抓取，防止 SSRF 和恶意大文件。

### 7.3 协作与持久化

第一版可以用普通 REST 保存版本快照；多人协作成熟后再把画布文档映射为 Yjs shared types，并用 Hocuspocus 提供同步。

建议分离：

- 持久数据：节点、边、位置、尺寸、层级、提示词、参数、资产引用、任务记录和版本。
- 用户会话：当前视口、选中项、面板状态、临时输入和本地快捷键偏好。
- 实时 presence：光标、用户颜色、正在拖动的节点和当前视口；不要把每一次无意义的 UI 状态写入持久版本。

## 8. 性能与体验的硬约束

1. 不要在画布上同时播放所有视频。非焦点视频显示封面或低码率代理，进入视口后再加载，离开视口暂停并释放资源。
2. 大文件和原图不进入 React/Vue 状态树或 CRDT；节点只持有稳定 ID 和缩略图 URL。
3. 拖拽期间只更新必要的坐标：React 使用 memo/useCallback，Vue 使用稳定的响应式引用和 computed，原生 Web 使用 requestAnimationFrame 合并指针事件。React Flow 官方性能文档也明确提醒节点移动会产生高频状态更新。
4. 画布需要有缩放级别策略：远景显示点位/封面，近景显示缩略图，选中后才显示完整参数和操作栏。
5. 对生成任务做增量执行：只重跑受参数或上游资产版本影响的下游节点；ComfyUI 的缓存/部分图执行和 InvokeAI 的节点缓存可以作为后端实现参考。
6. 生成节点必须区分 `queued`、`running`、`succeeded`、`failed`、`canceled`、`expired`，并提供重试、取消、查看错误和恢复输出的入口。
7. 视频生成通常是异步长任务，第一版应优先交付 5 秒左右的图生视频和首帧预览，再扩展长视频拼接、时间轴和音频合成。

## 9. 分阶段落地建议

### 阶段一：可用 MVP

- 根据现有前端栈选择 React Flow + Zustand、Vue Flow + Pinia，或 Drawflow/LiteGraph.js + 轻量自定义 store。
- 文本、上传、图片生成、视频生成、结果预览四类节点。
- 先接一个托管 Provider 或 InvokeAI；统一服务端任务状态。
- 画布快照、工作流 JSON 导入导出、缩略图、重试和图生视频。
- 对象存储、封面抽取和基础权限，不做实时多人协作。

### 阶段二：可复用工作流

- Provider 注册表和能力声明，按输入类型校验连接。
- 节点缓存、批量运行、局部重跑、输出版本和提示词变量。
- 接入 ComfyUI 作为可选 GPU Worker，或使用 Diffusers 构建专用推理服务。
- FFmpeg 抽帧、拼接、转码、字幕和音频节点。

### 阶段三：协作与高级创作

- Yjs + Hocuspocus 实时协作、光标、评论和权限。
- Konva/Fabric 局部像素编辑或蒙版工作区；不要把编辑器状态和生成 DAG 混成一个不可迁移的对象。
- 长视频时间轴、分镜、首尾帧衔接、资产库和团队模板。

## 10. 最终选型建议

| 模块 | 推荐组合 | 适用理由 |
| --- | --- | --- |
| React | React Flow + Zustand + 可选 React Konva + Provider Gateway + 对象存储 + BullMQ + FFmpeg | React 节点生态和完整 AI 画布参考项目最多；适合已有 React 产品快速验证工作流。 |
| Vue | Vue Flow + Pinia + 可选 Vue Konva + Provider Gateway + 对象存储 + BullMQ + FFmpeg | Vue 3 产品不需要迁移框架；Vue Flow 覆盖节点画布基础交互，Vue Konva 补自由素材编辑。 |
| 原生 Web | Drawflow 或 LiteGraph.js + Fabric/Konva + 自定义 store + Provider Gateway | 依赖少、嵌入和桌面 WebView 友好；代价是交互、状态、可访问性和历史能力需要自己维护。 |
| 跨框架工作流 | Rete.js 核心 + 对应 React/Vue/Lit 渲染插件 + 各自 UI 层 | 适合未来需要同时支持 React、Vue 和原生组件，或需要把 dataflow/control flow 引擎独立维护的团队。 |
| 自建 GPU 后端 | 上述任一前端 + InvokeAI；必要时再接 Diffusers 或独立 ComfyUI Worker | 前端技术栈不影响生成后端；InvokeAI 的 Apache-2.0 和 HTTP 队列更适合作为商业自托管起点，ComfyUI 则提供更广的模型生态但有 GPL-3.0 合规成本。 |

**最终原则：**不要为了画布迁移已有前端框架。已有 React 就从 React Flow 开始，已有 Vue 3 就从 Vue Flow 开始，原生项目优先 Drawflow/LiteGraph.js；只有在明确需要跨框架共享图执行引擎时，才把 Rete.js 作为公共核心。后端统一使用 Provider Gateway，避免画布组件绑定具体模型。
